# 账号体系设计与落地说明

> 目标：让用户能登录，**登录后对话历史跟着账号走**（换设备、重装、容器重启都不丢）；
> 未登录时仍然能用，且登录那一刻把本机游客数据自动搬进账号。

---

## 一、先看结论：三条硬门槛决定方案可行性

这是**唯一必须先确认的事**——它决定「手机号一键登录」和「App 微信登录」到底能不能做。

| 能力 | 个人主体 | 个体工商户 / 企业主体 | 费用 |
|---|---|---|---|
| 小程序静默登录（`wx.login` → openid） | ✅ 可用 | ✅ 可用 | 免费 |
| 小程序 **手机号一键登录**（`getPhoneNumber`） | ❌ **不可用** | ✅ 可用 | 微信认证 **300 元/年** + **0.03 元/次**（前 1000 次免费） |
| 小程序获取真实昵称/头像 | ❌ 仅匿名「微信用户」+ 灰头像 | ⚠️ 需用户主动授权（`chooseAvatar` / 昵称填写） | 免费 |
| 小程序 **UnionID**（跨端识别同一人） | ❌ **拿不到** | ✅ 需绑定微信开放平台 | 开放平台认证 300 元/年 |
| **App 移动应用微信登录** | ❌ **无法申请** | ✅ 可用 | 企业认证 **300 元/年** |
| 短信验证码登录（自建） | ✅ 可用 | ✅ 可用 | 按条计费（约 0.03–0.05 元/条） |
| 小程序**服务类目**（婚恋交友 / AI 情感咨询） | ❌ **个人主体不能选**，过不了审 | ✅ 可选 | — |

### 关键政策原文依据

1. **个人类型账号暂不支持微信认证**，而「微信开放平台账号必须完成开发者资质认证才可以绑定同主体小程序」
   —— 所以个人主体小程序**拿不到 UnionID**，也就无法与其它端打通为同一账号。
   <https://developers.weixin.qq.com/miniprogram/introduction/>
2. **个人主体小程序不支持 `getPhoneNumber`**，调用报错码 102；获取手机号需**非个人主体 + 微信认证**，
   且是**付费能力**（0.03 元/次）。
3. **移动应用（App）微信登录**：微信开放平台的移动应用必须**企业/组织**主体并完成认证，个人账号无法申请。

### 结论（针对本项目）

> 「恋爱大师」是 **AI 情感咨询 + 聊天**类应用。个人主体小程序**连服务类目都过不了**
> （社交/婚恋、AI 生成内容均不在个人开放类目内），所以**主体升级是绕不开的前提**，
> 不是为了手机号登录才去认证。

**因此推荐路线：**

- **主体**：注册**个体工商户**（成本最低，可线上办理）→ 小程序**微信认证 300 元/年**。
  这样手机号一键登录、UnionID、App 微信登录**三件事一起解决**。
- **主体暂时不升级时**：走**方案 A（手机号 + 短信验证码自建账号）**，三端可用、零资质门槛，
  已在本项目**实现并验证通过**（见第五节）。

## 二、账号模型：为什么是「用户 + 多身份」而不是「一张表塞 openid」

核心设计是**账号与登录方式解耦**：

```
app_user（账号）              app_user_identity（登录身份）
┌────────────────────┐        ┌──────────────────────────────────────┐
│ id  ← 就是 user_id │◄───────│ user_id                              │
│ nickname           │        │ provider  phone / wechat_miniapp / …  │
│ avatar             │        │ app_id    小程序 AppID（openid 只在小程序内唯一）│
│ phone              │        │ open_id   手机号 或 微信 openid        │
│ status             │        │ union_id  跨端唯一（需开放平台绑定）    │
│ register_from      │        │ session_key                          │
└────────────────────┘        └──────────────────────────────────────┘
         ▲                                  唯一键 (provider, app_id, open_id)
         │
    chat_session.user_id   ← 对话历史直接挂账号，实现跨设备同步
```

**为什么不把 openid 直接放 user 表？**

| 场景 | 多身份表 | 单表塞 openid |
|---|---|---|
| 用户先微信登录，后绑手机号 | 加一行 identity | 加一堆可空列 |
| 再支持公众号 / App 登录 | 再加一行 | 再改表结构 |
| 用户想解绑某个登录方式 | 删一行 | 列置空 + 判断逻辑 |
| openid 在不同小程序可能重复 | 唯一键带 `app_id`，天然正确 | 极易踩坑 |

**唯一键必须是 `(provider, app_id, open_id)`**，不能只按 `open_id`：
微信 openid 只在**单个应用内**唯一，换一个小程序同一个人 openid 就变了。

## 三、交互流程设计

### 3.1 手机号登录 / 注册（注册与登录合一）

```
用户                          前端                          后端                        短信服务
 │                             │                             │                            │
 │ ① 输入手机号                │                             │                            │
 │ ② 点「获取验证码」          │                             │                            │
 ├────────────────────────────►│ POST /api/auth/sms/send     │                            │
 │                             ├────────────────────────────►│ 限频校验(同号60s/单日10条)  │
 │                             │                             ├───────────────────────────►│
 │                             │                             │  生成6位码 → 落库(5分钟有效) │
 │                             │  ◄── {devCode?} 200         │◄───────────────────────────┤
 │ ③ 收到短信，倒计时 60s      │                             │                            │
 │ ④ 输入验证码 + 勾选协议     │                             │                            │
 │ ⑤ 点「登录 / 注册」         │                             │                            │
 ├────────────────────────────►│ POST /api/auth/login/phone  │                            │
 │                             ├────────────────────────────►│ 校验并消费验证码(一次性)     │
 │                             │                             │ 查 identity(phone, phone)  │
 │                             │                             │  ├ 命中 → 取已有账号        │
 │                             │                             │  └ 未命中 → 建账号(=注册)   │
 │                             │  ◄── {token, user} 200      │                            │
 │ ⑥ 登录成功，历史变云端      │ 存 token → 合并游客数据      │                            │
 │                             │ 后续请求自动带 Authorization │                            │
```

**要点：**

- **注册与登录同一个接口**：没查到手机号身份就建号，用户无感，少一个"注册"入口。
- **验证码一次性**：校验通过即置 `used=true`，防止重放。
- **限频两层**：同号 60 秒一次 + 单号单日 10 条，防刷短信费。
- **开发模式**：`SMS_PROVIDER=none` 时验证码直接回显在响应里（`devCode`），
  本地联调不需要真发短信；生产配 `tencent` 通道后该字段**不会出现**。

### 3.2 小程序微信授权登录（静默，不需要用户点授权框）

```
小程序                                             后端
  │                                                 │
  │ onLoad → uni.login({provider:'weixin'})         │
  │ 拿到临时凭证 code（5 分钟有效、一次性）          │
  ├────── POST /api/auth/login/wechat {code} ──────►│
  │                                                 │ 用 AppSecret 调 code2Session
  │                                                 │   → openid / session_key / unionid
  │                                                 │ 查 identity(wechat_miniapp, appid, openid)
  │                                                 │   ├ 命中 → 取已有账号
  │                                                 │   └ 未命中 → 建号
  │◄──────── {token, user} ────────────────────────┤
  │ 存 token，后续请求带 Authorization              │
```

**要点：**

- `AppSecret` **只在服务端使用**，绝不下发前端（前端只拿 code）。
- 校验 `appId` 与服务端配置一致，防止拿别家小程序的 code 换本服务的登录态。
- 微信错误码做了中文映射：40029 凭证失效 / 45011 频率限制 / 40226 高风险账号。
- 微信登录**不弹授权框**，符合微信官方「先静默拿 openid 建账号，需要头像昵称时再按需引导」的建议。

### 3.3 账号绑定与合并（本项目最容易被忽略、但必须处理的一环）

真实世界一定会出现「同一个人有两个账号」：

> 用户先用微信快登建了账号 B，后来在账号页想绑手机号，结果发现这个号早就注册过账号 A。

`POST /api/auth/bind/phone` 的处理规则：

```
绑手机号 P → P 已被账号 A 占用？
 ├ 否 → 直接把 (phone, P) 身份挂到当前账号，完成绑定
 └ 是 → 当前账号是不是「空壳」？
         判定 = 除本次微信身份外没有其它登录方式 且 没有任何对话历史
          ├ 是（空壳）→ 把当前账号的身份全迁到 A，当前账号删除，返回 switched=true
          │              （用户其实是在"登录已有账号"，只是入口走了微信）
          └ 否（有数据）→ 409 拒绝，提示「请改用手机号登录」
                         绝不静默吞掉用户数据
```

**两个安全细节：**

1. **`switched=true` 时后端会返回新的 token**，前端必须用它覆盖本地登录态
   （旧账号已删除，旧 token 会 401）——本项目前端已处理。
2. `autoMerge: false` 可以在前端做二次确认后关闭自动合并。

### 3.4 游客数据合并（登录不丢历史）

```
未登录时：对话写入「游客空间」
         首次运行生成 guest-<随机16位>（一设备一空间，避免两台设备互看）
         同时打标记 LM_GUEST_LEGACY（老版本的游客数据写在 default 空间）

登录成功时：
   对 guestSpacesToMerge() 返回的每个空间调用 POST /api/auth/merge-guest
       → ['default', 'guest-3f2a...']   迁移会话的 user_id 归属
   迁移成功 → 清掉 legacy 标记
```

> ⚠️ 实现陷阱：`guestSpacesToMerge()` 必须**先调 `getGuestId()` 再读 legacy 标记**。
> legacy 标记是在 `getGuestId()` 内部写入的，顺序反了会让 `default` 被漏掉，
> 游客数据迁不过去。**这个 bug 是被自动化测试抓出来的**（见第五节）。

### 3.5 数据归属与越权防护

| 请求方 | 数据归属 | 说明 |
|---|---|---|
| 带有效 token | **以 token 中的 user 为准**，忽略请求里的 `user_id` | 防止伪造 `user_id` 写进别人账号 |
| 无 token（游客） | 只允许操作 `default` / `guest-*` 空间 | 否则任何人改一下 `user_id` 就能读写他人历史 |
| 访问非本人会话 | 返回 404（不是 403） | 不泄露"这个会话是否存在" |

## 四、接口清单（前缀 `/api/auth`）

| 方法 | 路径 | 鉴权 | 说明 |
|---|---|---|---|
| GET | `/config` | 公开 | 能力开关：`smsDevMode` / `wechatMiniAppLogin` / `wechatAppLogin` |
| POST | `/sms/send` | 公开 | 发验证码；`scene=login\|bind`；开发模式返回 `devCode` |
| POST | `/login/phone` | 公开 | 手机号+验证码，未注册自动注册 → `{token,user}` |
| POST | `/login/wechat` | 公开 | 小程序 code 换登录态（服务端 code2Session） |
| POST | `/bind/phone` | 需登录 | 绑手机号，冲突时可合并空壳账号 |
| POST | `/merge-guest` | 需登录 | 游客历史迁到当前账号 |
| GET | `/me` | 需登录 | 账号信息 + 已绑定登录方式 |
| POST | `/profile` | 需登录 | 改昵称/头像 |
| POST | `/logout` | 需登录 | 退出（登录态无状态，前端清 token） |

**登录态**：自签 **HS256 JWT**，`payload={sub,iat,exp,jti}`，默认 30 天。
服务端不存 session，水平扩容无需共享存储。签名用**标准库 `hmac`+`hashlib` 手写**，
不引入 PyJWT/python-jose —— 少一个依赖，云托管构建更稳。

**中间件白名单**：`/api/auth` 必须免产品级 API Key，
否则"要先带 Key 才能登录"会形成死锁（见 `app/core/middleware.py`）。

## 六、App 能授权微信账号登录吗？——结论与替代方案

### 结论

**现阶段不能。** 微信开放平台的**移动应用**必须**企业/组织主体并完成认证**，个人账号无法申请该能力。

即使将来升级了主体，还需要：

| 平台 | 需要提交 |
|---|---|
| Android | 应用**包名** + **32 位 MD5 签名**（注意：不是 SHA1） |
| iOS | Bundle ID + **Universal Links** |
| 通用 | 企业认证 300 元/年，审核 1–7 个工作日；未上架应用的能力有次数限制 |

### 如果一定要打通「小程序 ↔ App 同账号」

必须满足 **两个条件同时成立**：

1. 小程序和移动应用**绑定到同一个微信开放平台账号**（互为同主体）；
2. 两头都做微信登录，后端用 **UnionID** 作为账号识别锚点。

只要有一头拿不到 UnionID（个人主体就是这种情况），就只能**退化为用手机号当跨端唯一键**。

### 替代方案（按推荐度排序）

| 方案 | 体验 | 前提 |
|---|---|---|
| **A. 手机号 + 短信验证码**（本项目已实现） | 用户要点 2–3 次、输 6 位码 | 无资质门槛，三端通用，成本约 0.03–0.05 元/条 |
| B. 小程序一键登录 + App 也用手机号 | 小程序零输入，App 输手机号 | 需非个人主体 + 微信认证 |
| C. 小程序「微信登录 + 绑手机号」，App 走手机号进同一账号 | 小程序顺畅，App 输一次手机号 | 同上；靠手机号作为 unionid 的替代锚点 |
| D. App 内嵌 WebView 走公众号网页授权 | 体验割裂，不推荐 | 需认证服务号 |

> **注意**：方案 B/C 里，`getPhoneNumber` 只是「让用户少输一次手机号」的体验优化，
> **不解决跨端识别问题**——跨端识别靠的是 UnionID 或手机号本身。
> 所以即使升级了主体，**手机号仍然建议作为账号的稳定锚点**保留。

## 八、上线前必做（安全与合规）

- [ ] **`JWT_SECRET` 必须在云托管环境变量里显式配置**（形如 32 位随机串）。
      留空会退回内置开发密钥，密钥一换**所有用户登录态全部失效**。
- [ ] 数据库不可用时账号接口会返回 503，前端已有「账号服务未就绪」提示，不影响游客使用。
- [ ] 登录页已放《用户协议》《隐私政策》勾选，**未勾选不允许登录**（审核硬要求）。
- [ ] 手机号在返回体与日志中**全程脱敏**（`138****8888`）。
- [ ] 建议后续补：账号注销入口、验证码图片/行为验证（防刷）、登录日志审计。
