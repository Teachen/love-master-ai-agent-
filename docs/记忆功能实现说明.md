# 对话记忆功能 · 实现说明

> 本文档补充说明「恋爱大师」项目会话记忆功能的实现方式、与 LangChain / LangGraph 官方标准方案的差异，以及官方文档索引。
> README 中此前仅在目录结构与接口表中提及，无专门章节。

---

## 一、当前实现概览

项目采用**自研文件持久化方案**，未使用 LangChain 官方记忆抽象。

| 项目 | 说明 |
|---|---|
| 实现类 | `app/agent/memory.py` → `FileChatMemory` |
| 对标来源 | Java 版 `yu-ai-agent` 的 `FileBasedChatMemory`（LangChain4j） |
| 存储介质 | 本地 JSON 文件 `./tmp/memory/{session_id}.json` |
| 隔离粒度 | 按 `session_id` 一个会话一个文件 |
| 缓存 | 进程内字典 `_memory_pool`，`Dict[str, FileChatMemory]` |
| 上下文窗口 | `max_messages=20`（约 10 轮），超出丢弃最早消息 |
| 历史恢复 | 实例化时 `_load()` 读盘，服务重启后历史不丢 |

### 数据结构

落盘格式为扁平数组，只保留角色与文本，不保留 `tool_calls`、`usage_metadata` 等字段：

```json
[
  { "type": "human", "content": "单身三年了怎么办" },
  { "type": "ai",    "content": "先聊聊你的感受……" }
]
```

### 关键方法

| 方法 | 职责 |
|---|---|
| `_load()` / `_save()` | 读盘 / 落盘；读失败时告警并重置，不抛异常 |
| `add_user_message()` / `add_ai_message()` | 追加消息 → 裁剪 → 立即落盘 |
| `get_messages()` | 返回消息列表，供 Prompt 注入 |
| `get_history_text()` | 拼成「用户：… / 恋爱大师：…」纯文本，供 Agent 用 |
| `clear()` | 清空内存列表并写入空数组 |
| `_trim()` | 保留最后 `max_messages` 条 |

### 会话池

```python
_memory_pool: Dict[str, FileChatMemory] = {}

def get_chat_memory(session_id: str) -> FileChatMemory:
    if session_id not in _memory_pool:
        _memory_pool[session_id] = FileChatMemory(session_id)
    return _memory_pool[session_id]
```

## 二、调用链路

```
POST /api/chat  { message, session_id, mode }
   │
   ▼
api/chat.py   _build_app(session_id) → LoveApp(session_id)
   │
   ▼
app/love_app.py   构造函数内置 self.memory = get_chat_memory(session_id)
   │
   ├─ mode=chat  → chat()          history 走 MessagesPlaceholder("history")
   ├─ mode=rag   → chat_with_rag() 同上，附加知识库上下文
   └─ mode=agent → run_agent()     history 走 get_history_text() 拼纯文本
   │
   ▼
回答生成后：memory.add_user_message() + memory.add_ai_message() 回写 JSON
```

### 三种模式的注入方式差异（重要）

**chat / rag 模式** —— 标准消息列表注入，语义正确：

```python
prompt = ChatPromptTemplate.from_messages([
    ("system", system_prompt or LOVE_SYSTEM_PROMPT),
    MessagesPlaceholder("history"),
    ("human", "{input}"),
])
chain = prompt | llm | StrOutputParser()
answer = chain.invoke({"history": self.memory.get_messages(), "input": message})
```

**agent 模式** —— 历史被降级为纯文本，塞进一个 HumanMessage：

```python
# app/agent/react_agent.py:96
content = question if not history else f"【历史对话】\n{history}\n\n【当前问题】\n{question}"
result = self.graph.invoke({"messages": [HumanMessage(content=content)]}, ...)
```

这是当前实现中最值得改进的一点，详见第四节。

## 三、接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/chat` | 统一入口，`mode` 三选一 |
| POST | `/api/chat/rag` | 知识库问答 |
| POST | `/api/chat/agent` | 智能体推理 |
| GET | `/api/chat/history?session_id=xxx` | 查询历史，返回 `[{role, content}]` |
| DELETE | `/api/chat/history?session_id=xxx` | 清空历史 |

请求/响应模型见 `app/schemas/chat.py`（`ChatRequest` / `HistoryResponse`）。

示例：

```bash
curl -X POST http://localhost:8000/api/chat \
  -H "Content-Type: application/json" \
  -d "{\"message\":\"单身三年了，越来越焦虑怎么办？\",\"session_id\":\"user_001\",\"mode\":\"chat\"}"

curl "http://localhost:8000/api/chat/history?session_id=user_001"

curl -X DELETE "http://localhost:8000/api/chat/history?session_id=user_001"
```

## 四、与官方标准方案的差异

### 4.1 未继承 `BaseChatMessageHistory`

LangChain 官方定义了统一抽象 `langchain_core.chat_history.BaseChatMessageHistory`，要求实现 `messages` 属性与 `add_message()` / `clear()`。

**官方文档中给出的文件式实现示例与本项目的 `FileChatMemory` 几乎同构**（官方示例类名 `FileChatMessageHistory`，同样是 `storage_path + session_id` + JSON 读写）。差异在于：

- 官方示例 `messages` 是 `@property`，每次访问都读盘；本项目改为内存持有 + 显式 `_save()`，性能更好，但也就此脱离了官方接口。
- 未继承的后果：无法直接接入 `RunnableWithMessageHistory`、LangGraph checkpointer 等官方生态组件，需要额外适配层。

### 4.2 LangGraph 已装但未启用 checkpointer（最值得改的点）

`requirements.txt` 已包含：

```
langgraph==0.2.60
langgraph-checkpoint==2.0.9
```

但 `ReActAgent._build_graph()` 编译时**没有传 checkpointer**：

```python
return graph.compile()          # 当前
# 官方标准写法：
# return graph.compile(checkpointer=checkpointer)
```

官方 LangGraph 持久化机制是 Agent 多轮记忆的推荐做法：编译时挂 checkpointer，调用时传 `thread_id`，框架自动在每步后保存/恢复状态。改用后 `react_agent.py` 里那段「手工拼 `【历史对话】` 字符串」的代码可以整段删除，历史以真实消息序列进入模型，`tool_calls` 上下文也不再丢失。

代价：`thread_id` 与现有 `session_id` 需做映射；内存版 `MemorySaver` 重启即丢，落库需 `langgraph-checkpoint-postgres`（项目未装）。

### 4.3 只有短期记忆，无长期记忆

| 能力 | 本项目 | 官方方案 |
|---|---|---|
| 短期（会话内多轮） | ✅ 滑动窗口 20 条 | checkpointer / chat_history |
| 长期（跨会话，用户画像） | ❌ 无 | LangGraph Store |
| 超窗处理 | 直接丢弃 | 摘要压缩 / 裁剪策略 |

## 五、已知薄弱点

1. **并发无锁**
   `_memory_pool` 为进程内全局字典。同一 `session_id` 并发请求会同时修改 `_messages` 并整文件覆写，产生竞态覆盖。
   多进程部署（`uvicorn --workers N`）下问题更严重：每个进程各持独立内存副本，写同一个文件必然互相踩踏。

   **建议**：加 per-session 文件锁（如 `filelock`），或将存储后端整体换成 Redis / PostgreSQL。

2. **`clear()` 不删文件**
   `clear_chat_memory()` 写入空数组后从池中移除，但 JSON 文件保留为空文件，`tmp/memory` 目录只增不减。

3. **agent 模式历史降级为文本**
   见 4.2，历史以纯文本形式进入 `HumanMessage`，模型无法区分真实的多轮消息边界，也无法携带工具调用上下文。

4. **无历史长度上限保护**
   `max_messages` 限制的是消息**条数**而非**字符数**。单条消息最长 2000 字符（`ChatRequest` 约束），20 条最坏情况约 4 万字符，可能挤占上下文窗口。

5. **时间戳缺失**
   落盘不含时间字段，无法实现按时间的记忆衰减或会话过期清理。

## 七、改造建议（按优先级）

| 优先级 | 改造项 | 涉及文件 | 复杂度 |
|---|---|---|---|
| P0 | 加 per-session 文件锁，消除并发覆盖 | `app/agent/memory.py` | 低 |
| P1 | ReActAgent 接入 LangGraph checkpointer | `app/agent/react_agent.py` | 中 |
| P1 | `FileChatMemory` 继承 `BaseChatMessageHistory`，兼容官方生态 | `app/agent/memory.py` | 低 |
| P2 | 新增 Redis / PostgreSQL 存储后端，支持多进程部署 | 新增 `app/agent/stores/` | 中 |
| P2 | 超窗时摘要压缩替代直接丢弃 | `app/agent/memory.py` | 中 |
| P3 | 落盘增加时间戳，支持 TTL 过期清理 | `app/agent/memory.py` | 低 |
