# 短信验证码开通指南（阿里云）

> 面向「手机号 + 验证码」登录。目标：把「发送验证码不可用」变成一条能自己走通的路径。
> 代码侧通道实现在 `app/api/auth.py`，配置项在 `app/config/settings.py`。

---

## 一、先定位「不可用」到底是哪一层

点「发送验证码」拿到什么，就说明卡在哪一层。**四层里前三层都跟阿里云无关**，
先排除掉再谈开通，能省很多时间。

| 现象 | 真实原因 | 怎么修 |
|---|---|---|
| `503 账号服务未就绪：验证码与账号都要落库` | **数据库没开**（`MYSQL_ENABLED=false`） | 见第二节。本地默认就是关的，这是最常见的一层 |
| `503 短信服务未配置` | `SMS_PROVIDER=none` 且是生产环境（刻意拦截，防止验证码外泄） | 配一个真实通道，见第四节 |
| `502 短信发送失败（通道 xxx）：...` | 通道参数不全 / 签名模板未审核 / 运营商报备未完成 | 看提示里的错误码，对照第六节 |
| `429 发送过于频繁` | 60 秒内重复点 | 等一会儿。早期版本里「发送失败」也会占掉这个名额，已修 |
| `400 手机号格式不正确` | 号码不合法 | 输入 11 位大陆手机号 |

### 自检接口

不用翻日志，直接问服务端还缺什么：

```bash
curl http://localhost:8000/api/health/config
```

关注这几个字段：

```json
{
  "sms": "aliyun_pnvs",        // 当前通道
  "smsReady": false,           // 能不能真发出去
  "smsMissing": [              // 还缺哪几项，直接照这个变量名去填
    "ALIYUN_ACCESS_KEY_ID",
    "ALIYUN_SMS_SIGN_NAME"
  ]
}
```

`smsReady: true` 且 `smsMissing: []` 才算配好。登录页拉到的 `/api/auth/config`
也会带上 `smsProvider` / `smsReady`，前端据此能给出比 502 更清楚的提示。

## 二、第一步：先把本地登录跑通（5 分钟）

> **本节是「省钱起步」路线**（`SMS_PROVIDER=none`，不发真短信）。
> 若你的目标就是**测试环境和生产环境都真发短信**，可跳过本节直接看下面 2.1。

**账号体系（验证码、用户、登录态）都要落库**，而本地 `.env.dev` 默认 `MYSQL_ENABLED=false`。
只要这一项是关的，登录接口一律 503 —— 这跟短信通道配没配毫无关系。

本地建议直接用 sqlite 自测，不需要安装 MySQL：

```ini
# .env.dev
MYSQL_ENABLED=true
MYSQL_HOST=sqlite:///./tmp/dev.db
SMS_PROVIDER=none          # 开发模式：不发短信，验证码回显在响应里
```

重启后端，进登录页点「发送验证码」，页面会把回显的验证码直接显示出来（点一下自动填入）。
**到这里登录链路就是通的**，后面换真实短信只是替换「怎么把码送到用户手机上」这一环。

> `SMS_PROVIDER=none` 在 `APP_ENV=prod` 下会被强制忽略并返回 503。
> 这是刻意设计：生产环境回显验证码 = 任何人用任意手机号请求就能拿到码，直接接管账号。

### 2.1 测试环境与生产环境都真发短信

当前项目的实际配置就是这条路线：`.env.dev` 与 `.env.prod` **都是 `aliyun_pnvs`**。

| 环境 | 配置文件 | `SMS_PROVIDER` | 是否真发 | 是否回显验证码 |
|---|---|---|---|---|
| 本地 / 测试 | `.env.dev` | `aliyun_pnvs` | ✅ 真发 | ❌ 不回显 |
| 生产（云托管） | `.env.prod` + 控制台环境变量 | `aliyun_pnvs` | ✅ 真发 | ❌ 不回显 |
| （可选）省钱联调 | 临时把 `SMS_PROVIDER` 改成 `none` | `none` | ❌ 不发 | ✅ 回显 |

三个必须知道的副作用：

1. **真发就不再回显验证码**。这不是 bug：
   `settings.sms_dev_code_exposed` 对真实通道恒为 `false`。
   真发了还回显，等于任何人拿任意手机号请求就能取到别人的验证码。联调看手机短信即可。
2. **本地和线上共用同一份阿里云频控额度**（按号码算：1 条/分钟、5 条/小时、10 条/天）。
   本地连点会把线上的额度吃掉，表现为 App 报 `biz.FREQUENCY`，
   很容易误判成"线上配置坏了"。
   → **把常用测试号加进号码认证控制台「通用设置」的白名单**（最多 300 个，
   白名单号码**不受流控**），本地和线上就互不干扰了。
3. **会产生费用**。阿里云有赠送额度，用尽后按条扣费，建议给短信钱包设余额告警。

怎么确认某个环境到底会不会真扣钱（不用登服务器、不用猜）：

```
GET /api/health/config
```

看三个字段：`smsRealSend`（true = 会真发）、`smsReady`（配置是否齐全）、
`smsDevCodeExposed`（是否回显，生产必须为 false）。

本地想临时切回"不发真短信"：`SMS_PROVIDER=none` + **重启后端**
（uvicorn 热重载不监听 `.env` 文件），改回来同理。

## 三、选路线：阿里云有两个产品，个人账号能用的只有一个

这是最容易踩的坑，先看清楚再动手，否则会在「申请签名」这一步反复失败。

| | 短信服务（dysmsapi） | 号码认证服务 · 短信认证（dypnsapi） |
|---|---|---|
| 项目里对应配置 | `SMS_PROVIDER=aliyun` | `SMS_PROVIDER=aliyun_pnvs` |
| 实名认证要求 | **仅支持企业实名认证**（个人可用「他用资质」= 关联一家企业的营业执照 + 盖章授权委托书） | **个人实名认证即可** |
| 短信签名 | 自己申请，需资质匹配 + 运营商实名报备 | 用平台**赠送**的签名，不能自定义（且赠送签名必须搭配赠送模板） |
| 短信模板 | 自己申请，审核 2–4 小时 | 用平台**赠送**模板 |
| 签名审核 / 报备 | 签名审核最快 24 小时；通过后还要运营商实名报备，**平均 5–7 个工作日，部分 7–10 个工作日** | 无需自己报备（用赠送签名，已就绪） |
| 适合谁 | 需要品牌签名（短信里显示【你的公司】）的企业 | 个人开发者、想尽快跑通、不在意签名显示为阿里云分配的名字 |

**结论**：个人账号请走 `aliyun_pnvs`。它把最耗时的「资质 → 签名 → 运营商报备」整段跳过了，
拿到 AccessKey 就能发。代价只是短信前面的【】里是阿里云分配的名字，不是你的品牌。

> 顺带一个利好：号码认证的短信认证属于「用了才计费」，短信提交成功但运营商回执失败时**不计费**。

## 四、路线 A：号码认证「短信认证」（个人推荐）

### 1. 开通

1. 注册阿里云账号并完成**个人实名认证**（支付宝扫码最快）。
2. 打开号码认证服务控制台 → 概览页 → **开通服务**。
   <https://dypns.console.aliyun.com/overview>
3. 开通后进入 **短信认证服务 → 短信认证参数管理**，在「签名配置」「模板配置」两个页签里
   各挑一个平台赠送的签名和模板，记下它们的名字与 Code（例如签名 `速通互联验证码`、模板 `100001`）。
   - 赠送签名 **必须** 搭配赠送模板使用，混用自定义的会发不出去。

### 2. 创建 AccessKey（用 RAM 子账号，别用主账号）

1. 访问 <https://ram.console.aliyun.com/profile/access-keys> 创建 AccessKey。
2. 建议先建 RAM 用户，只授予 **`AliyunDypnsFullAccess`**（号码认证服务权限）。
3. 记下 AccessKeyId / AccessKeySecret。**Secret 只在创建时显示一次**，关掉页面就再也看不到。

### 3. 填进项目

本地联调（密钥写 `.env`，它已被 `.gitignore` 排除；`.env.dev` 会入库，禁止写密钥）：

```ini
# .env.dev（开关，无密钥）
SMS_PROVIDER=aliyun_pnvs
ALIYUN_SMS_SIGN_NAME=速通互联验证码
ALIYUN_SMS_TEMPLATE_CODE=100001
ALIYUN_SMS_CODE_PARAM=code

# .env（密钥）
ALIYUN_ACCESS_KEY_ID=LTAI****************
ALIYUN_ACCESS_KEY_SECRET=************************
```

云托管：生成变量清单再粘贴到控制台，比手敲不容易漏项：

```bash
python tmp/gen_cloudrun_env.py     # 产出 tmp/cloudrun_env.json（含 JWT_SECRET、短信通道等）
```

> 云托管控制台「服务设置 → 基本信息 → 环境变量」支持 JSON 粘贴。

### 4. 验证

重启后端，先自检再实发：

```bash
curl http://localhost:8000/api/health/config       # smsReady 应为 true
curl -X POST http://localhost:8000/api/auth/sms/send \
     -H "Content-Type: application/json" \
     -d '{"phone":"13800000000"}'
```

`{"ok": true, "phone": "138****0000"}` 且手机收到短信即为成功。
控制台「发送记录」也能看到每条的运营商回执。

## 五、路线 B：短信服务（企业认证）

只有在「必须显示自己的品牌签名」时才需要走这条，环节多、耗时长。

1. **开通服务**：注册 + 企业实名认证 → 短信服务控制台开通服务。
   <https://dysms.console.aliyun.com/>
2. **申请资质**（2025 年起为必填前置）：控制台 → 资质管理 → 新增资质，提交
   企业证件、法人材料、短信业务管理员材料。资质通过后才能申请签名。
3. **申请签名**：签名来源可选「企事业单位全称或简称 / 工信部备案网站全称或简称 /
   App 全称或简称 / 公众号或小程序全称或简称」。审核预计最快 24 小时（工作时间提交更快）。
   - 你的网站已备案（`闽ICP备2022001906号`），**备案网站名称**是可用的签名来源之一，
     前提是备案主体与阿里云账号的资质主体一致。
4. **申请模板**：类型选「验证码」，内容形如
   `您的验证码为${code}，5分钟内有效，请勿泄露。` 审核预计 2–4 小时。
5. **等运营商实名报备**：签名审核通过**不等于**能立刻发。系统会自动向三大运营商报备，
   平均 5–7 个工作日，部分情况 7–10 个工作日或更长。期间部分运营商方向发送失败属正常现象。
   - 在控制台「签名管理」页查看三大运营商的报备状态。
   - 保持发送活跃度（建议每网每天 10 条以上、一周至少 3 天有发送量）有助于报备尽快通过。
6. 创建 AccessKey（RAM 子账号 + `AliyunDysmsFullAccess`），配置同路线 A，只是
   `SMS_PROVIDER=aliyun`，且签名/模板换成自己申请的。

### 计费与限额（两条路线共通）

- 仅在发送时计费；可购买套餐包，超出后按量扣余额。
- 国内短信 70 字以内算 1 条，超过 70 字按 67 字/条拆分计费。
- 验证码类模板的变量**不超过 6 个字符**（我们发的是 6 位数字，符合）。
- 阿里云侧单号码限频：**1 天 20 条**；SendSms 单账号 QPS 5000/秒。
- 控制台可绑定最多 **5 个测试手机号**用于体验发送（会产生费用）。

## 六、常见错误码对照

| 报错 | 含义 | 怎么处理 |
|---|---|---|
| `isv.SMS_SIGNATURE_ILLEGAL` | 签名不存在 / 未审核通过 / 与资质不匹配 | 检查签名名是否与控制台完全一致，是否已通过审核 |
| `isv.SMS_TEMPLATE_ILLEGAL` | 模板不存在或未通过审核 | 检查模板 Code，注意是 Code 不是模板名 |
| `isv.PARAM_LENGTH_LIMIT` / `isv.TEMPLATE_PARAMS_ILLEGAL` | 模板变量不匹配 | 变量名要与模板里的 `${xxx}` 完全一致，即 `ALIYUN_SMS_CODE_PARAM` |
| `isv.AMOUNT_NOT_ENOUGH` | 账户余额不足 | 充值或购买套餐包 |
| `isv.MOBILE_NUMBER_ILLEGAL` | 号码格式错误 | 用 11 位大陆手机号 |
| `isv.BUSINESS_LIMIT_CONTROL` / `isv.DAY_LIMIT_CONTROL` | 触发流控 | 阿里云侧单号 1 天 20 条；本地我们自己还有 60 秒间隔 + 单日上限 |
| `FUNCTION_NOT_OPENED` | 还没开通该功能 | 号码认证控制台里没点「开通服务」 |
| `SignatureDoesNotMatch` / `InvalidSignature` | 签名算错 | 已按官方规则实现；重点确认 AccessKeySecret 没截断、服务器时间没跑偏 |
| `InvalidTimeStamp` | 时间戳超期 | 签名有效期 31 分钟，校一下服务器时间（NTP） |
| ` biz.FREQUENCY` / `600016` / `check frequency failed` | **号码认证侧发送频次超限**（限流，不是配置错） | 见下面 6.1 |
| `isv.INVALID_PARAMETERS`（签名或者模版无效） | SignName / TemplateCode 不是本账号的赠送签名/赠送模板 | 见下面 6.2 |
| `Throttling` | 请求过频 | 降频重试（官方建议超时 ≥1s 再判重试） |

完整列表见官方错误中心，以上是最容易撞到的几个。

### 6.1 `biz.FREQUENCY: check frequency failed` —— 最容易被误判成配置错

**先说结论：这是限流，不是配置错误。**

判断依据很简单：报错从「配置不完整」（`smsMissing` 非空 / 502 提示缺 `ALIYUN_SMS_*`）
升级成「阿里云返回了一个业务错误码」，说明 **AccessKey、签名、模板都已经配通了** ——
否则阿里云连这个接口都不会让你调进去，只会回 `InvalidAccessKeyId.NotFound` 之类的鉴权错误。

对应号码认证（dypnsapi）SDK 错误码 **600016 = 验证码发送频次超出限制**。默认阈值：

| 维度 | 默认上限 | 窗口怎么算 |
|---|---|---|
| 同一号码 | 1 条/分钟 | **整点自然窗口**，不是滚动 60 秒 |
| 同一号码 | 5 条/小时 | **整点自然窗口**（如 10:00–10:59） |
| 同一号码 | 10 条/天 | 滚动 24 小时 |
| 同一号码跨签名 | 40 条/天 | 滚动 24 小时 |

> 具体次数以控制台为准：号码认证服务 → **通用设置** → 查看/调整发送频次。
> 短信服务（dysmsapi）侧对应的是 `isv.BUSINESS_LIMIT_CONTROL`，
> 在短信服务控制台「发送频率设置」里调（**企业认证账号才能调，个人不支持**）。

**处理办法（按推荐顺序）**：

1. **等**：分钟级等 60 秒；小时级等**过整点**（比如 10:58 发的，11:00 就能再发）；
   天级等 24 小时。注意别在等待期间反复点——每点一次都会重新计时。
2. **换一个手机号测试**：验证「是号码被限」还是「账号被限」。
3. **加白名单**：号码认证控制台 → 通用设置 → 把常用测试号加进白名单
   （最多 **300 个**，白名单号码**不受流控限制**）。开发阶段强烈建议先把自己的号加进去。
4. **调阈值**：控制台「通用设置」里适当调高每小时/每天次数。

**别和项目自身的限频搞混**（两者会叠加，症状很像但处理不同）：

| 来源 | 表现 | 在哪看 |
|---|---|---|
| 项目自身 | HTTP **429**，「发送过于频繁，请 N 秒后再试」/「今日验证码次数已达上限」 | `SMS_SEND_INTERVAL`（默认 60 秒）、`SMS_DAILY_LIMIT`（默认 10 条/天） |
| 阿里云侧 | HTTP **502**，`短信发送失败（通道 aliyun_pnvs）：... biz.FREQUENCY` | 见本节 |

想确认到底是哪一个，直接看页面的 HTTP 状态码：**429 是我们拦的，502 是阿里云回的**。
另外 `GET /api/health/config` 的 `smsReady` / `smsMissing` 可以确认配置层面没问题，
`smsMissing` 为空却仍失败，就一定是限流或号码本身的问题。

### 6.2 `isv.INVALID_PARAMETERS: 签名或者模版无效` —— 门户调试成功但 App 发送失败

真实踩坑记录（2026-09-26）：**同一个账号，阿里云 OpenAPI 门户调试 `SendSmsVerifyCode` 返回
`Code=OK`，App 走后端发送却报「签名或者模版无效」**。

根因：两边用的参数**根本不是同一套**。
门户调试是在网页上现填的（当时填的是赠送签名 + 赠送模板 CODE），
而**后端读的是部署环境的环境变量** —— 云托管控制台里配的还是早先把
**模板名称**（`验证绑定手机号模板`）当成签名、模板 CODE 填成旧值（`100005`）的那套。
签名/模板本身是好的，坏的是后端读到的那两行配置。

排查三步：

1. **看后端实际读到的值**（不用登服务器）：
   `GET /api/health/config` → `smsSignName` / `smsTemplateCode`
2. **与调试成功的参数逐字比对**：OpenAPI 门户调试结果里能看到当时的 `SignName` / `TemplateCode`；
   或到号码认证控制台「短信认证参数管理」看赠送签名与赠送模板。
3. **不一致就改环境变量并重新发布**：
   - 微信云托管：控制台 → 服务设置/环境变量 → 改 `ALIYUN_SMS_SIGN_NAME` / `ALIYUN_SMS_TEMPLATE_CODE`
     → **重新发布版本**（只改变量不发布不会生效）。
   - 本地：改 `.env.prod` / `.env.dev` 后**重启进程**（uvicorn 热重载不监听 `.env*`）。

常见的三种填错姿势（都会报这个错）：

| 填错姿势 | 例子 |
|---|---|
| 把模板**名称**填进签名 | `验证绑定手机号模板`（这是模板名，不是签名「恒启众」） |
| 模板 CODE 用了旧的/别的服务的 | 已废弃的 `100005`，实际是 `100001` |
| 赠送签名搭配了自申模板（或反之） | 赠送签名只能配赠送模板 |

### 6.3 名字全对却仍报「签名或者模版无效」→ 查 AccessKey 的身份

第 6.2 节的坑修完后，本项目**还继续报同一个错**。这次的名字确实是对的
（`恒启众` / `100001`，已用 `/api/health/config` 核对），于是往下挖了一层。

**关键实验：对照法**

故意编一个绝对不存在的签名和模板去调，对比错误码：

```python
# 真实配置
send(SignName="恒启众", TemplateCode="100001")        # → isv.INVALID_PARAMETERS
# 编造的配置
send(SignName="绝对不存在的签名ZZZ", TemplateCode="999999")  # → isv.INVALID_PARAMETERS（一模一样）
```

两者报错完全相同，说明**该身份下没有任何可用签名/模板** —— 问题不在名字。

**再查 AccessKey 到底是谁**：

```python
# sts 服务，Version 用 2015-04-01
_aliyun_rpc_post("sts.aliyuncs.com", "GetCallerIdentity", {"Version": "2015-04-01"})
```

本项目的返回：

```
IdentityType = RAMUser                                  ← 是 RAM 子账号，不是主账号
AccountId    = 1934803592834063
Arn          = acs:ram::1934803592834063:user/power-application-user
```

**两个可能原因，按可能性排序**：

1. **RAM 子账号没有被授权号码认证**。
   主账号 → RAM 访问控制 → 用户 `power-application-user` → 添加权限 →
   **`AliyunDypnsFullAccess`**（号码认证服务）；若还用到短信服务再加 `AliyunDysmsFullAccess`。
2. **号码认证开通在另一个阿里云账号下**。
   `AccountId` 必须与「号码认证控制台」所在的账号一致。
   去控制台右上角看账号 ID，和上面 `AccountId` 比对 —— 不一致就是这个问题，
   需要用开通了号码认证的那个账号创建 AccessKey。

> ⚠️ **最容易误判的点**：阿里云 OpenAPI 门户的「调试」用的是你**登录态的身份**，
> 它和 AccessKey 的权限**不是一回事**。门户里发得出去，不代表这个 AK 发得出去。
> 这在多账号 / RAM 子账号场景下几乎必踩。

**一条命令跑完全部自检**（不发真实短信、不花钱）：

```bash
python tmp/diag_pnvs_send.py
```

它依次输出：后端读到的签名/模板（含隐藏字符检查）→ AK 的真实身份 →
真实签名 vs 编造签名的对照结果 → 结论。用**明显非法的号码**当探针，
参数错误会立刻被拒，不会真发出去；每组换新号码，避免被频控污染成 `biz.FREQUENCY`。

### 6.4 最终真相：签名名库里只有「同主体」的签名能实际下发

权限、参数格式都排除后**仍报同样的错**，最后把「签名配置」页签里的 **6 个系统赠送签名逐个实测**（探针号非法、零成本），结果：

| 签名（签名配置页签里显示"已通过"） | 实测结果 |
|---|---|
| 恒启众 | ❌ isv.INVALID_PARAMETERS |
| **北京恒创联众** | ✅ 过校验（推进到手机号校验） |
| **恒创联众科技** | ✅ 过校验 |
| 恒锐创信 | ❌ |
| 恒创众联科技 | ❌ |
| 北京恒创联信 | ❌ |

**规律：只有「恒创联众」字样（同主体）的签名能配对本账号的赠送模板。**
签名名库里其他主体的签名虽然显示"审核通过"，但只是"可见"，配你的模板会被拒。
（连"恒创联众"这个不在列表里的简写都能过 —— 校验对同主体签名做了包含匹配。）

**最终配置**：

```ini
SMS_PROVIDER=aliyun_pnvs
ALIYUN_SMS_SIGN_NAME=北京恒创联众      # 用实测能通过的；别用恒启众
ALIYUN_SMS_TEMPLATE_CODE=100001        # 填模板 CODE，不是模板名称"登录/注册模板"
ALIYUN_SMS_CODE_PARAM=code
```

模板名称和模板 CODE 的对应关系（模板配置页签）：**接口只认 CODE**：

| 模板名称 | 模板 CODE | 适用场景 |
|---|---|---|
| 登录/注册模板 | **100001** | ✅ 本项目用这个 |
| 修改密码模板 | 100002 | 改密场景 |
| 重置密码模板 | 100003 | 重置场景 |
| 绑定新手机号模板 | 100004 | 换绑场景 |
| 验证绑定手机号模板 | 100005 | 绑定场景 |

> 💡 `ILLEGAL_MOBILE` 是好消息信号：校验顺序是「签名/模板 → 手机号」，
> 报手机号错误 = 签名和模板都已经通过校验（探针用的是故意非法的号码）。

### 6.5 最终修复：弃用 `##code##` 占位符，验证码由服务端生成直接传值

签名换对后（6.4），真实号码上还剩最后一个错：
**`请检查模板内容与模板参数是否匹配`** —— 这是 `##code##` 占位符的问题。

官方文档写了两种传值方式，但**实测本账号/模板下只有第二种能发成功**：

```
方式一（文档示例）：TemplateParam = {"code":"##code##","min":"5"}   ← 实测被拒
方式二（实测可用）：TemplateParam = {"code":"123456","min":"5"}     ← Code=OK，短信送达
```

> 修正日期 2026-09-26 23:20：真实号码发送返回 `Code=OK`，短信成功送达。
> 方式一被拒的具体原因未知（文档与实测不符），不排除与赠送模板类型有关；
> 如果阿里云后续修复，可以再切回方式一（验证码由阿里云生成更防篡改）。

**代码改动**（`app/api/auth.py::_send_sms_by_aliyun_pnvs`）：

1. `TemplateParam` 直接传**服务端自己生成的 6 位验证码**（不再用 `##code##`）
2. `min` 传验证码有效期的分钟数（`ValidTime / 60`，与短信内容里的"$min$分钟内有效"一致）
3. 去掉 `ReturnVerifyCode` / `AutoRetry`（不再需要阿里云回传验证码）
4. 函数返回值 = 入参 code（自己生成的），与上层落库逻辑天然一致

**教训**：官方文档写的参数组合也可能与实际不符 —— 遇到"文档说支持但实测被拒"时，
果断换实测可用的写法，并留好注释说明为什么不用官方推荐方式。

**全链路验证记录**：

```
23:17  探针脚本直接调阿里云：真实号码 + 实际验证码 → Code=OK，短信送达
23:2x  走完整接口 POST /api/auth/sms/send → {"ok":true}（旧孤儿进程抢先应答过一次，
       清掉后成功——见第八章「后端没跟着更新时的排查」）

**方法论沉淀**（这次排查了近一小时才定位，四条都值回票价）：

1. 签名"显示已通过"≠"能配你的模板"，**必须逐个实测**。
2. 限流/频控错误会掩盖参数校验错误 —— 对照实验**每组换一个新探针号码**。
3. 门户调试用的是登录态身份，与 AccessKey 的权限不是一回事。
4. 官方文档与实测不符时，以实测为准，并在代码注释里说明偏离原因。
```

## 七、防盗刷

短信是按条计费的，验证码接口一旦被刷就是直接烧钱。两层都要有：

**阿里云侧**：短信服务控制台有防盗刷监控与频率限制设置，务必开起来；给短信钱包单独设余额告警。

**项目侧**（已在代码里）：

| 机制 | 默认值 | 配置项 |
|---|---|---|
| 同一手机号发送间隔 | 60 秒 | `SMS_SEND_INTERVAL` |
| 同一手机号单日上限 | 10 条 | `SMS_DAILY_LIMIT` |
| 验证码有效期 | 300 秒 | `SMS_CODE_TTL` |
| 生产禁回显验证码 | 强制 | `SMS_ALLOW_DEV_CODE_IN_PROD` 保持 false |

另外，公网服务建议打开 `API_KEY_ENABLED=true`（`/api/auth` 已在免鉴权白名单内，
不会造成「要先带 Key 才能登录」的死锁）。

## 八、代码侧说明（给后来改的人）

- 通道分派在 `app/api/auth.py::_send_sms_real`，返回**实际下发的验证码**而不是入参。
  这不是多余的：阿里云号码认证由服务端生成验证码，与本地生成的不一样，
  上层必须拿返回值落库，否则用户收到的码和库里的码对不上，永远提示「验证码不正确」。
- 阿里云两个通道共用 `_aliyun_rpc_post`（RPC 风格 V1 签名：`HMAC-SHA1` + `Base64`）。
  签名里三个必踩的坑都写在函数注释里：`/` 必须编码成 `%2F`（Python `quote` 默认 `safe='/'`）、
  `Signature` 不能参与自身签名、`AccessKeySecret` 后要补一个 `&` 当 HMAC 密钥。
- 发送失败会**删掉刚插入的那行验证码**。不删的话它会占掉「60 秒间隔」和「单日上限」的名额，
  用户改完配置想立刻重试会被自己的失败记录挡住。
- `sms_dev_mode` 判定是「provider 是否在 `REAL_SMS_PROVIDERS` 里」，不是「是否等于 tencent」。
  后者在加新通道时会静默失效：配了阿里云却被当成开发模式，生产环境既不真发也不回显，登录直接死。
- 阿里云的错误码**不能原样丢给用户**：`biz.FREQUENCY`（限流）和 `FUNCTION_NOT_OPENED`（没开通）
  的解法完全相反。曾经这里对所有失败统一附加一句「（FUNCTION_NOT_OPENED = 还没开通短信认证）」，
  结果用户真实遇到限流时被误导去反复开通服务。现在改成 `_ALIYUN_ERROR_HINTS` 表按错误码分流
  （精确 → 前缀 → 子串），未命中的错误码**不乱猜**，只透传原始 Code/Message。
- 回归测试：`tmp/test_sms_aliyun.py`（签名构造、参数完整性、错误码分流与透传、验证码回落）。
