# 短信验证码开通指南（阿里云）

> 面向「手机号 + 验证码」登录。目标：把「发送验证码不可用」变成一条能自己走通的路径。
> 代码侧通道实现在 `app/api/auth.py`，配置项在 `app/config/settings.py`。

---

## 一、先定位「不可用」到底是哪一层

点「发送验证码」拿到什么，就说明卡在哪一层。**四层里前三层都跟阿里云无关**，
先排除掉再谈开通，能省很多时间。

| 现象 | 真实原因 | 怎么修 |
|---|---|---|
| `503 账号服务未就绪：验证码与账号都要落库` | **数据库没开**（`MYSQL_ENABLED=false`） | 见第二节。本地默认就是关的，这是最常见的一层 |
| `503 短信服务未配置` | `SMS_PROVIDER=none` 且是生产环境（刻意拦截，防止验证码外泄） | 配一个真实通道，见第四节 |
| `502 短信发送失败（通道 xxx）：...` | 通道参数不全 / 签名模板未审核 / 运营商报备未完成 | 看提示里的错误码，对照第六节 |
| `429 发送过于频繁` | 60 秒内重复点 | 等一会儿。早期版本里「发送失败」也会占掉这个名额，已修 |
| `400 手机号格式不正确` | 号码不合法 | 输入 11 位大陆手机号 |

### 自检接口

不用翻日志，直接问服务端还缺什么：

```bash
curl http://localhost:8000/api/health/config
```

关注这几个字段：

```json
{
  "sms": "aliyun_pnvs",        // 当前通道
  "smsReady": false,           // 能不能真发出去
  "smsMissing": [              // 还缺哪几项，直接照这个变量名去填
    "ALIYUN_ACCESS_KEY_ID",
    "ALIYUN_SMS_SIGN_NAME"
  ]
}
```

`smsReady: true` 且 `smsMissing: []` 才算配好。登录页拉到的 `/api/auth/config`
也会带上 `smsProvider` / `smsReady`，前端据此能给出比 502 更清楚的提示。

## 二、第一步：先把本地登录跑通（不发真短信，5 分钟）

**账号体系（验证码、用户、登录态）都要落库**，而本地 `.env.dev` 默认 `MYSQL_ENABLED=false`。
只要这一项是关的，登录接口一律 503 —— 这跟短信通道配没配毫无关系。

本地建议直接用 sqlite 自测，不需要安装 MySQL：

```ini
# .env.dev
MYSQL_ENABLED=true
MYSQL_HOST=sqlite:///./tmp/dev.db
SMS_PROVIDER=none          # 开发模式：不发短信，验证码回显在响应里
```

重启后端，进登录页点「发送验证码」，页面会把回显的验证码直接显示出来（点一下自动填入）。
**到这里登录链路就是通的**，后面换真实短信只是替换「怎么把码送到用户手机上」这一环。

> `SMS_PROVIDER=none` 在 `APP_ENV=prod` 下会被强制忽略并返回 503。
> 这是刻意设计：生产环境回显验证码 = 任何人用任意手机号请求就能拿到码，直接接管账号。

## 三、选路线：阿里云有两个产品，个人账号能用的只有一个

这是最容易踩的坑，先看清楚再动手，否则会在「申请签名」这一步反复失败。

| | 短信服务（dysmsapi） | 号码认证服务 · 短信认证（dypnsapi） |
|---|---|---|
| 项目里对应配置 | `SMS_PROVIDER=aliyun` | `SMS_PROVIDER=aliyun_pnvs` |
| 实名认证要求 | **仅支持企业实名认证**（个人可用「他用资质」= 关联一家企业的营业执照 + 盖章授权委托书） | **个人实名认证即可** |
| 短信签名 | 自己申请，需资质匹配 + 运营商实名报备 | 用平台**赠送**的签名，不能自定义（且赠送签名必须搭配赠送模板） |
| 短信模板 | 自己申请，审核 2–4 小时 | 用平台**赠送**模板 |
| 签名审核 / 报备 | 签名审核最快 24 小时；通过后还要运营商实名报备，**平均 5–7 个工作日，部分 7–10 个工作日** | 无需自己报备（用赠送签名，已就绪） |
| 适合谁 | 需要品牌签名（短信里显示【你的公司】）的企业 | 个人开发者、想尽快跑通、不在意签名显示为阿里云分配的名字 |

**结论**：个人账号请走 `aliyun_pnvs`。它把最耗时的「资质 → 签名 → 运营商报备」整段跳过了，
拿到 AccessKey 就能发。代价只是短信前面的【】里是阿里云分配的名字，不是你的品牌。

> 顺带一个利好：号码认证的短信认证属于「用了才计费」，短信提交成功但运营商回执失败时**不计费**。

## 四、路线 A：号码认证「短信认证」（个人推荐）

### 1. 开通

1. 注册阿里云账号并完成**个人实名认证**（支付宝扫码最快）。
2. 打开号码认证服务控制台 → 概览页 → **开通服务**。
   <https://dypns.console.aliyun.com/overview>
3. 开通后进入 **短信认证服务 → 短信认证参数管理**，在「签名配置」「模板配置」两个页签里
   各挑一个平台赠送的签名和模板，记下它们的名字与 Code（例如签名 `速通互联验证码`、模板 `100001`）。
   - 赠送签名 **必须** 搭配赠送模板使用，混用自定义的会发不出去。

### 2. 创建 AccessKey（用 RAM 子账号，别用主账号）

1. 访问 <https://ram.console.aliyun.com/profile/access-keys> 创建 AccessKey。
2. 建议先建 RAM 用户，只授予 **`AliyunDypnsFullAccess`**（号码认证服务权限）。
3. 记下 AccessKeyId / AccessKeySecret。**Secret 只在创建时显示一次**，关掉页面就再也看不到。

### 3. 填进项目

本地联调（密钥写 `.env`，它已被 `.gitignore` 排除；`.env.dev` 会入库，禁止写密钥）：

```ini
# .env.dev（开关，无密钥）
SMS_PROVIDER=aliyun_pnvs
ALIYUN_SMS_SIGN_NAME=速通互联验证码
ALIYUN_SMS_TEMPLATE_CODE=100001
ALIYUN_SMS_CODE_PARAM=code

# .env（密钥）
ALIYUN_ACCESS_KEY_ID=LTAI****************
ALIYUN_ACCESS_KEY_SECRET=************************
```

云托管：生成变量清单再粘贴到控制台，比手敲不容易漏项：

```bash
python tmp/gen_cloudrun_env.py     # 产出 tmp/cloudrun_env.json（含 JWT_SECRET、短信通道等）
```

> 云托管控制台「服务设置 → 基本信息 → 环境变量」支持 JSON 粘贴。

### 4. 验证

重启后端，先自检再实发：

```bash
curl http://localhost:8000/api/health/config       # smsReady 应为 true
curl -X POST http://localhost:8000/api/auth/sms/send \
     -H "Content-Type: application/json" \
     -d '{"phone":"13800000000"}'
```

`{"ok": true, "phone": "138****0000"}` 且手机收到短信即为成功。
控制台「发送记录」也能看到每条的运营商回执。

## 五、路线 B：短信服务（企业认证）

只有在「必须显示自己的品牌签名」时才需要走这条，环节多、耗时长。

1. **开通服务**：注册 + 企业实名认证 → 短信服务控制台开通服务。
   <https://dysms.console.aliyun.com/>
2. **申请资质**（2025 年起为必填前置）：控制台 → 资质管理 → 新增资质，提交
   企业证件、法人材料、短信业务管理员材料。资质通过后才能申请签名。
3. **申请签名**：签名来源可选「企事业单位全称或简称 / 工信部备案网站全称或简称 /
   App 全称或简称 / 公众号或小程序全称或简称」。审核预计最快 24 小时（工作时间提交更快）。
   - 你的网站已备案（`闽ICP备2022001906号`），**备案网站名称**是可用的签名来源之一，
     前提是备案主体与阿里云账号的资质主体一致。
4. **申请模板**：类型选「验证码」，内容形如
   `您的验证码为${code}，5分钟内有效，请勿泄露。` 审核预计 2–4 小时。
5. **等运营商实名报备**：签名审核通过**不等于**能立刻发。系统会自动向三大运营商报备，
   平均 5–7 个工作日，部分情况 7–10 个工作日或更长。期间部分运营商方向发送失败属正常现象。
   - 在控制台「签名管理」页查看三大运营商的报备状态。
   - 保持发送活跃度（建议每网每天 10 条以上、一周至少 3 天有发送量）有助于报备尽快通过。
6. 创建 AccessKey（RAM 子账号 + `AliyunDysmsFullAccess`），配置同路线 A，只是
   `SMS_PROVIDER=aliyun`，且签名/模板换成自己申请的。

### 计费与限额（两条路线共通）

- 仅在发送时计费；可购买套餐包，超出后按量扣余额。
- 国内短信 70 字以内算 1 条，超过 70 字按 67 字/条拆分计费。
- 验证码类模板的变量**不超过 6 个字符**（我们发的是 6 位数字，符合）。
- 阿里云侧单号码限频：**1 天 20 条**；SendSms 单账号 QPS 5000/秒。
- 控制台可绑定最多 **5 个测试手机号**用于体验发送（会产生费用）。

## 六、常见错误码对照

| 报错 | 含义 | 怎么处理 |
|---|---|---|
| `isv.SMS_SIGNATURE_ILLEGAL` | 签名不存在 / 未审核通过 / 与资质不匹配 | 检查签名名是否与控制台完全一致，是否已通过审核 |
| `isv.SMS_TEMPLATE_ILLEGAL` | 模板不存在或未通过审核 | 检查模板 Code，注意是 Code 不是模板名 |
| `isv.PARAM_LENGTH_LIMIT` / `isv.TEMPLATE_PARAMS_ILLEGAL` | 模板变量不匹配 | 变量名要与模板里的 `${xxx}` 完全一致，即 `ALIYUN_SMS_CODE_PARAM` |
| `isv.AMOUNT_NOT_ENOUGH` | 账户余额不足 | 充值或购买套餐包 |
| `isv.MOBILE_NUMBER_ILLEGAL` | 号码格式错误 | 用 11 位大陆手机号 |
| `isv.BUSINESS_LIMIT_CONTROL` / `isv.DAY_LIMIT_CONTROL` | 触发流控 | 阿里云侧单号 1 天 20 条；本地我们自己还有 60 秒间隔 + 单日上限 |
| `FUNCTION_NOT_OPENED` | 还没开通该功能 | 号码认证控制台里没点「开通服务」 |
| `SignatureDoesNotMatch` / `InvalidSignature` | 签名算错 | 已按官方规则实现；重点确认 AccessKeySecret 没截断、服务器时间没跑偏 |
| `InvalidTimeStamp` | 时间戳超期 | 签名有效期 31 分钟，校一下服务器时间（NTP） |
| `Throttling` | 请求过频 | 降频重试（官方建议超时 ≥1s 再判重试） |

完整列表见官方错误中心，以上是最容易撞到的几个。

## 七、防盗刷

短信是按条计费的，验证码接口一旦被刷就是直接烧钱。两层都要有：

**阿里云侧**：短信服务控制台有防盗刷监控与频率限制设置，务必开起来；给短信钱包单独设余额告警。

**项目侧**（已在代码里）：

| 机制 | 默认值 | 配置项 |
|---|---|---|
| 同一手机号发送间隔 | 60 秒 | `SMS_SEND_INTERVAL` |
| 同一手机号单日上限 | 10 条 | `SMS_DAILY_LIMIT` |
| 验证码有效期 | 300 秒 | `SMS_CODE_TTL` |
| 生产禁回显验证码 | 强制 | `SMS_ALLOW_DEV_CODE_IN_PROD` 保持 false |

另外，公网服务建议打开 `API_KEY_ENABLED=true`（`/api/auth` 已在免鉴权白名单内，
不会造成「要先带 Key 才能登录」的死锁）。

## 八、代码侧说明（给后来改的人）

- 通道分派在 `app/api/auth.py::_send_sms_real`，返回**实际下发的验证码**而不是入参。
  这不是多余的：阿里云号码认证由服务端生成验证码，与本地生成的不一样，
  上层必须拿返回值落库，否则用户收到的码和库里的码对不上，永远提示「验证码不正确」。
- 阿里云两个通道共用 `_aliyun_rpc_post`（RPC 风格 V1 签名：`HMAC-SHA1` + `Base64`）。
  签名里三个必踩的坑都写在函数注释里：`/` 必须编码成 `%2F`（Python `quote` 默认 `safe='/'`）、
  `Signature` 不能参与自身签名、`AccessKeySecret` 后要补一个 `&` 当 HMAC 密钥。
- 发送失败会**删掉刚插入的那行验证码**。不删的话它会占掉「60 秒间隔」和「单日上限」的名额，
  用户改完配置想立刻重试会被自己的失败记录挡住。
- `sms_dev_mode` 判定是「provider 是否在 `REAL_SMS_PROVIDERS` 里」，不是「是否等于 tencent」。
  后者在加新通道时会静默失效：配了阿里云却被当成开发模式，生产环境既不真发也不回显，登录直接死。
- 回归测试：`tmp/test_sms_aliyun.py`（签名构造、参数完整性、错误码透传、验证码回落）。
